# Laporan Tes: INC-001 (recon ke WordPress)

Tes kedua Hermes + WOLFSTRIKE. Berbeda dari [INC-002](INC-002.md), insiden ini hanya recon tanpa bukti server dibobol. Tujuannya cek apakah Hermes bisa menahan diri: tidak membesar-besarkan severity dan tidak mengarang kompromi.

**Tanggal tes:** 15 Nov 2026
**Hasil singkat:** Hermes tidak overclaim. Kesimpulan "tidak ada bukti server dibobol, severity MEDIUM" tepat, dan output tool yang salah dikoreksi sendiri. Tapi satu aktivitas mencurigakan dari 2018 terlewat dan dilabeli normal. Setelah skill `threat-investigation` diberi aturan cakupan per-IP, [tes ulang](#tes-ulang-setelah-aturan-cakupan) menangkap aktivitas itu, dan [uji 3 run](#uji-konsistensi-3-run) menunjukkan hasilnya stabil. Yang belum stabil: kalibrasi severity dan akurasi ID MITRE.

## Setup

Sama dengan [INC-002](INC-002.md#setup): Hermes v0.23.1, `glm-5.3-flash`, WOLFSTRIKE lokal, VirusTotal tidak dikonfigurasi.

Provider model sempat tidak stabil (HTTP 503 `model_temporarily_unavailable` dan 504). Hermes otomatis retry, jadi durasi tes ikut molor.

## Dataset

| File | Isi |
|---|---|
| `inc01-wordpress-apache-access.log` | Access log Apache, WordPress `10.1.2.111` / `greek.spenlab.local`, 894 baris |

Catatan: log tidak urut waktu dan berisi dua periode (Jul 2018 dan Mar 2020).

## Prosedur

Sama dengan INC-002: satu prompt `hermes chat -q`, ringkas log pakai pencarian, panggil `intake_incident` → `triage_incident` → `map_mitre_attack` → `extract_iocs` → `respond_and_report` (`executeBlock: false`), tanpa tool VirusTotal. Prompt hanya menyebut lokasi log dan server; tidak ada petunjuk soal isi insiden.

## Hasil

**Alur:** jalan. Durasi 9 menit 7 detik (termasuk retry provider), 4 perintah/script read-only, 7 pemanggilan tool. Log server mengonfirmasi kelima tool terpanggil. Tidak ada yang diblokir; blokir `10.18.200.87` hanya diusulkan dan menunggu persetujuan.

**Kesimpulan Hermes:**

- **Tidak ada bukti server dibobol.** Keyakinan tinggi bahwa ini hanya recon/scanning, keyakinan sedang bahwa server benar-benar aman karena buktinya hanya access log.
- Severity **MEDIUM**, naik ke HIGH kalau `10.18.200.87` ternyata bukan aset resmi.
- Penyerang: `10.18.200.87` (internal), 21 Mar 2020 11:41–12:14 (+0700).

| Waktu (+0700) | Kejadian |
|---|---|
| 11:42 | `GET /info.php` → 200 (phpinfo terekspos) |
| 11:45–11:46 | Akses `/wp-admin/maint/repair.php`, `/wp-content/`, plugin akismet |
| 11:58–12:10 | 4× `POST /xmlrpc.php`, 3 di antaranya memakai UA IE6 palsu |
| 12:03–12:05 | Directory listing `/wp-content/uploads/` terbuka, PDF diunduh |
| 12:06–12:07 | WPScan v3.7.7: 357 request, ratusan probe tema (404) |
| 12:07:23 | `/wp-login.php?action=register` → 302 (registrasi user tampaknya aktif) |
| 12:13–12:14 | Directory listing `/wp-includes/` |

MITRE ATT&CK (dipetakan oleh model): T1595.002 Vulnerability Scanning, T1592.002 Gather Victim Host Information: Software.

**Yang dikerjakan dengan baik:**

- Tidak overclaim. Hermes eksplisit menyebut fase Kill Chain berhenti di Reconnaissance, sebelum Exploitation.
- Output tool yang salah dikoreksi: triage bilang "Exploitation/C2" dan `map_mitre_attack` bilang T1059, keduanya ditolak karena tidak didukung bukti.
- IOC dipilah: `wpscan.org` (domain vendor tool, muncul di User-Agent), loopback, dan klien lain ditandai sebagai noise, bukan target blokir.
- Rekomendasi hardening relevan: hapus `info.php`, matikan directory listing, batasi `xmlrpc.php`, tutup registrasi, upgrade WordPress 4.0.x.

## Yang terlewat

Hermes melabeli `10.18.200.26` sebagai "browsing normal". Padahal pada 16 Jul 2018 IP ini:

| Waktu (+0700) | Kejadian |
|---|---|
| 11:02–11:04 | `?author=1`, `?author=2`: enumerasi user |
| 11:05:14 | `GET /?p=14'`: probe SQL injection |
| 11:05:57 | `POST /wp-comments-post.php` → 302 |
| 11:07:35 | `POST /wp-comments-post.php` → **500** |
| 12:01 | Homepage `GET /` → **500** berulang (5×). Sebelumnya 200. |

Ini belum tentu kompromi (penyebab 500 tidak terlihat dari access log), tapi jelas bukan browsing normal dan layak masuk laporan sebagai aktivitas mencurigakan terpisah. Kemungkinan penyebab terlewat: Hermes memfokuskan pencarian pada IP dengan request terbanyak dan periode 2020, sehingga aktivitas kecil di periode lain tidak diperiksa.

Hermes juga menulis "hasil triage WOLFSTRIKE: severity MEDIUM, setuju". Padahal `triage_incident` masih placeholder yang selalu mengembalikan `medium` kalau severity tidak diisi, jadi "setuju" di sini tidak bermakna.

## Tes ulang (setelah aturan cakupan)

Skill `threat-investigation` diberi bagian baru **Cakupan Analisa Log Mentah**: inventaris semua IP/User-Agent/path (stacking), periksa ekor panjang dan setiap periode, cek pola serangan per IP apa pun volumenya, beri verdict untuk setiap IP, dan akui batas cakupan. Dasarnya praktik threat hunting (stacking / long-tail analysis) dan temuan bahwa LLM cenderung melewatkan event di tengah tumpukan log.

Prompt identik dengan tes pertama. Durasi 5 menit 57 detik, kelima tool terpanggil, tidak ada blokir.

| | Tes 1 | Tes ulang |
|---|---|---|
| `10.18.200.26` (2018) | Dilabeli "browsing normal" | **Tertangkap**: enumerasi author, probe SQLi `?p=14%27`, 2× POST komentar (302, 500), homepage 500 berulang. Hubungan probe dengan error 500 ditulis sebagai hipotesis keyakinan rendah. |
| Verdict per IP | Hanya IP utama | Semua IP: `.87` serangan, `.26` recon/probe, `.181`, `.211`, loopback normal (dengan alasan) |
| Periode | Fokus Mar 2020 | Jun 2018 – Mar 2020, per periode |
| Kesimpulan dibobol | Tidak ada bukti (keyakinan tinggi) | Tidak terbukti (keyakinan sedang, dengan alasan batas bukti) |
| Severity | MEDIUM | Dampak MEDIUM, exposure HIGH |
| Batas cakupan | Sebagian | Eksplisit: isi POST, penyebab 500 (butuh error log), integritas file, aktivitas setelah log berakhir |

**Yang memburuk di tes ulang:**

- **MITRE lebih longgar.** T1190 Exploit Public-Facing Application ditambahkan untuk percobaan yang tidak terbukti berhasil, dan T1059 dari tool dipertahankan dengan keyakinan rendah. Di tes 1 T1059 ditolak. Selain itu T1592.001 (Hardware) seharusnya T1592.002 (Software).
- **Fase kill chain** disebut "Exploitation (percobaan)", di tes 1 "Reconnaissance". Keduanya bisa dibela, tapi ini menunjukkan output belum konsisten antar run.
- **Severity input ke pipeline** diisi `high`, lalu `triage_incident` (placeholder) mengembalikannya apa adanya. Hermes menyebutnya "verdict triage tool: severity high", padahal tool hanya menggemakan input.
- **Usulan blokir `10.18.200.26`** untuk aktivitas 2018 kurang relevan; tetap menunggu persetujuan.
- Tabel cakupan per IP tidak dibuat sebagai tabel terpisah; verdict ditulis di dalam timeline.

**Kesimpulan:** aturan cakupan memperbaiki masalah utama (aktivitas kecil terlewat). Tapi hasilnya tetap bergantung pada kepatuhan model, dan ketelitian di bagian lain (MITRE) bisa bergeser antar run. Pra-proses deterministik di WOLFSTRIKE tetap dibutuhkan untuk hasil yang konsisten.

## Uji konsistensi (3 run)

Satu run tidak cukup untuk membedakan efek perubahan dari variasi antar run, jadi tes diulang 3 kali dengan prompt identik setelah dua perubahan tambahan:

- `triage_incident` dan `map_mitre_attack` sekarang mengembalikan `status: "not-implemented"` tanpa nilai karangan (sebelumnya selalu "Exploitation/C2" dan T1059).
- Aturan MITRE di skill dipertegas: pisahkan teknik **terbukti** dan **percobaan**, cek ulang ID sub-teknik, dan jangan kutip output `not-implemented` sebagai verdict.

**Ekspektasi** (dari analisa manual):

| # | Ekspektasi | Run A | Run B | Run C |
|---|---|---|---|---|
| 1 | `.26` ditandai mencurigakan | ✅ | ✅ | ✅ |
| 2 | `.87` recon/serangan | ✅ | ✅ | ✅ |
| 3 | Tidak terbukti dibobol | ✅ | ✅ | ✅ |
| 4 | Severity MEDIUM | ✅ | ❌ High | ⚠️ Medium-High |
| 5 | Tidak ada T1059 | ✅ | ✅ | ✅ |
| 6 | T1190 hanya sebagai percobaan | ✅ | ✅ | ✅ |
| 7 | Output tool `not-implemented` tidak dikutip sebagai verdict | ✅ | ✅ | ✅ |
| | Durasi | 9m41s | 8m29s | 8m30s |

**Kesalahan lain per run:**

- **Run A:** T1589.003 ditulis "Usernames"; T1589.003 sebenarnya *Employee Names*.
- **Run B:** T1590 ditulis "Gather Victim Identity Information" (seharusnya T1589; T1590 adalah *Network Information*). Nama method XML-RPC (`system.listMethods`, `pingback.ping`) ditulis sebagai fakta, padahal access log hanya mencatat ukuran respons (181/370/403 byte), jadi itu tebakan. Severity High dengan alasan "kampanye berulang 2018→2020" tanpa bukti kedua IP terkait.
- **Run C:** T1592.002 diberi nama "Software Discovery" (nama itu milik T1518; T1592.002 adalah *Software*). T1110 Brute Force masuk "percobaan", padahal tidak ada percobaan login yang terlihat (Run B justru menolak T1110 dengan alasan itu).
- **Run B dan C:** menyebut 3 POST `xmlrpc.php`, padahal ada 4.

Provider sempat memutus stream ("Response truncated") di Run A dan C; Hermes tetap menyelesaikan laporan.

**Kesimpulan:**

- **Stabil (3/3):** cakupan per IP (`.26` selalu tertangkap), kesimpulan "tidak terbukti dibobol", T1059 hilang, T1190 tidak diklaim berhasil, output placeholder tidak lagi dikutip sebagai verdict. Masalah yang memburuk di tes ulang sebelumnya (T1059, severity dari tool) sudah tidak muncul.
- **Belum stabil:** kalibrasi severity (1/3 tepat), akurasi ID/nama MITRE (setiap run punya minimal satu kesalahan), dan hitungan detail (4 POST jadi 3). Aturan cek ID di skill tidak cukup: model tetap salah menamai sub-teknik.
- Ini sejalan dengan referensi: aturan prompt memperbaiki *apa yang diperiksa*, tapi angka, ID, dan kalibrasi butuh sumber deterministik.

## Saran

1. ~~Tambahkan aturan cakupan per IP di skill `threat-investigation`.~~ Sudah.
2. ~~Ubah output placeholder `triage_incident` dan `map_mitre_attack` jadi `not-implemented`.~~ Sudah.
3. **Rubrik severity di skill:** severity dinilai dari dampak yang terbukti; exposure/risiko lanjutan ditulis terpisah dan tidak menaikkan severity. Larang menghubungkan aktor antar periode tanpa bukti.
4. **Lookup MITRE deterministik:** `map_mitre_attack` sebaiknya memvalidasi ID dan nama terhadap dataset resmi ATT&CK (STIX dari MITRE), bukan mengandalkan ingatan model.
5. **Tool ringkasan log deterministik** di WOLFSTRIKE (inventaris semua IP, hitungan per endpoint, pola ala Sigma/Wazuh 31103, perubahan status) supaya angka seperti jumlah POST tidak meleset.
6. **Larang tebakan isi request:** isi POST yang tidak tercatat tidak boleh ditulis sebagai fakta; tulis sebagai hipotesis beserta dasarnya.
7. INC-001 dipakai sebagai tes regresi dengan tabel ekspektasi di atas; jalankan minimal 3 run setiap skill atau tool berubah.
